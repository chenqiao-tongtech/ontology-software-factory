# 第 19 篇｜让 Agent 按生产流程协作：工作流、状态机、依赖、重试与恢复

> **通往 AI 之桥｜本体论在 AI 工程中的实践 · 修订版 v2.0 软件工厂实战**  
> 本文接续上一章“Agent 岗位、Skills、上下文与输入输出契约”，把这些静态契约连接成可执行、可观测、可恢复的工作流。

想象一下：需求分析 Agent 已经给出结构化需求，架构 Agent 生成架构方案，开发 Agent 提交代码，测试 Agent 运行测试，安全 Agent 完成依赖审查。到这里，系统却突然卡住了——究竟是谁应该启动下一步？测试失败后能不能自动重试？重试会不会重复创建资源？谁批准发布？服务重启后，系统还能不能知道自己进行到哪里？

这不是“再给 Agent 一个更长的 Prompt”就能解决的问题。它是一个**工作流编排与运行治理**问题。

本篇的目标是把软件工厂从“有一组定义良好的 Agent”，推进到“有一条能追踪状态、执行策略、记录证据、处理失败的人机协作生产线”。配套代码会提供一个轻量 Python 工作流引擎、SQLite 运行记录、REST 风格接口，以及可操作的 Web 控制台。它是工程骨架与演示实现，不会假装已经接入真实 LLM、CI/CD 或生产 IAM。

## 一、为什么 Agent 越多，越需要显式工作流？

多 Agent 系统很容易从一张“角色分工图”开始：分析 Agent、架构 Agent、开发 Agent、测试 Agent、安全 Agent、发布 Agent……但角色图描述的是**谁有能力做什么**，并不自动回答以下问题：

- **顺序与依赖：** 安全审查必须等到代码与依赖清单生成后才能开始；部署必须等待测试、安全检查和人工批准。
- **状态与完成条件：** “Agent 回复了”不等于任务完成。一个节点只有在输出契约校验通过、必需证据齐全且副作用结果可核验时，才应被标记成功。
- **故障与恢复：** 网络暂时超时、模型限流、代码测试断言失败、权限拒绝，是性质不同的错误，不能采用统一的“失败就重试”。
- **人类决策：** 高风险操作需要暂停在明确的审批节点，而不是依赖 Agent 在自然语言中说一句“建议发布”。
- **审计与复盘：** 哪个版本的流程、哪个 Agent、哪次尝试、什么输入、产生了什么证据、谁批准了继续执行，都需要形成可查询的记录。

因此，软件工厂至少需要三个相互分离的对象：

| 对象 | 回答的问题 | 典型内容 |
|---|---|---|
| Agent / Skill 契约 | 谁可以做什么？ | 岗位、输入输出、工具权限、验收标准 |
| Workflow Definition | 任务按什么规则前进？ | 节点、依赖、状态转换、超时、重试、审批门 |
| Workflow Run | 这一次执行实际发生了什么？ | 当前状态、节点尝试、输入输出引用、证据、事件日志 |

这三个对象不应揉成一个巨大 Prompt，也不应混在一个不断变化的 JSON 变量里。定义负责描述规则，运行实例负责保存事实，编排器负责验证状态变化是否合法。

## 二、把“流程图”升级为可执行状态机

流程图通常只画出“需求 → 架构 → 开发 → 测试 → 安全 → 发布”。可执行的工作流还必须回答：每条边在什么条件下成立？失败会去哪？审批通过后如何恢复？重复收到同一个事件怎么办？

### 2.1 定义工作流中的核心本体

在本体层，我们至少需要以下概念：

- **WorkflowDefinition（工作流定义）：** 有名称、版本、开始条件、节点清单和策略。
- **WorkflowRun（工作流运行实例）：** 某个定义的一次执行，拥有稳定的 `runId`。
- **WorkflowStep（工作流节点）：** 一个可被编排的工作单元，执行模式可以是 Agent、系统任务或人工审批。
- **Dependency（依赖关系）：** 节点之间的前置条件。MVP 先支持有向无环图（DAG），避免隐式循环。
- **StepAttempt（节点尝试）：** 一次具体执行，记录开始时间、结束时间、错误类别和执行结果。
- **Evidence（证据）：** 测试报告、静态扫描结果、构建产物摘要、审批意见等可验证材料。
- **Approval（审批）：** 绑定具体运行、节点、决策人、决定和理由的独立对象。
- **WorkflowEvent（工作流事件）：** 记录状态变化、重试、暂停、审批和恢复等事实。
- **Policy（治理策略）：** 定义可重试错误、最大尝试次数、超时、审批要求、禁止的转换和副作用边界。

核心关系可以表达为：

```text
WorkflowDefinition 1 ── N WorkflowStep
WorkflowRun        N ── 1 WorkflowDefinition@version
WorkflowRun        1 ── N StepAttempt
WorkflowStep       N ── N WorkflowStep  (通过 Dependency 形成 DAG)
StepAttempt        1 ── N Evidence
WorkflowRun        1 ── N WorkflowEvent
WorkflowStep       0 ── 1 ApprovalGate（门控节点）
```

这里最关键的不是画得多漂亮，而是把**状态、关系、约束和证据**变成机器能检查的数据。比如：如果 `security-review` 依赖 `implementation`，编排器就不能在开发结果还没到达时启动安全审查；如果 `production-deploy` 需要人工批准，就不能因为模型输出了“风险可控”而绕过审批门。

### 2.2 运行状态与节点状态必须分开

工作流整体状态与单个节点状态不是一回事。

**运行实例状态（Run Status）**可从以下集合起步：

- `queued`：已创建，等待调度。
- `running`：存在可执行节点，流程正在推进。
- `waiting_approval`：暂停在人工审批门。
- `paused`：运维人员主动暂停，保留检查点。
- `failed`：当前运行遇到未恢复的失败。
- `succeeded`：所有必需节点成功或被策略允许地跳过。
- `cancelled`：运行被明确取消。

**节点状态（Step Status）**则至少包括：`pending`、`running`、`waiting_approval`、`succeeded`、`failed` 和 `cancelled`。

如果只有一个全局 `status` 字段，发生部分失败时就无法回答“哪个节点失败、哪些节点已完成、哪些节点还未开始”。反过来，如果每个节点都各自记录状态，却没有运行级状态，也很难为控制台列表、队列调度和恢复策略提供统一视图。

### 2.3 状态不是任意赋值，而是有守卫条件的转换

在 MVP 中，我们可以先定义这张表：

| 当前状态 | 事件 / 命令 | 守卫条件 | 结果 |
|---|---|---|---|
| `running` | `step.succeeded` | 当前节点确在运行，输出契约与必要证据通过校验 | 当前节点成功，调度下一个依赖已满足的节点 |
| `running` | `step.failed` | 已记录错误类别与本次尝试 | Run 失败；保留可恢复信息 |
| `failed` | `retry` | 失败节点可重试，且未超最大尝试次数 | 增加 attempt，重新排入执行 |
| `waiting_approval` | `approve` | 节点是审批门，意见非空，操作人有权限 | 审批节点成功，继续后续流程 |
| `waiting_approval` | `reject` | 操作人有权限且给出原因 | 节点失败，Run 进入失败状态 |
| `running` | `pause` | 运行未到终态 | 保留当前节点与上下文，运行进入暂停 |
| `paused` | `resume` | 运行未被取消且检查点可恢复 | 重新进入运行状态 |
| 非终态 | `cancel` | 符合取消策略 | 标记未开始节点为取消，并停止后续调度 |

**守卫条件（Guard）**是本体约束进入执行路径的地方。它要验证：依赖是否满足、工具调用是否授权、输入输出是否符合契约、证据是否存在、审批是否真实发生，以及操作是否可安全重复。

一个需要牢记的原则：**LLM 可以提出下一步建议，但状态转换必须由确定性的编排代码校验并提交。** 模型说“完成了”，最多是待验证的声明，不是数据库里的事实。

## 三、MVP 工作流：从需求到发布

本章的代码演示一条七节点的软件交付工作流：

1. **需求澄清（`requirement-analysis`）**：把自然语言意图整理成有验收标准的需求对象。
2. **架构设计（`architecture-design`）**：生成架构决策、模块边界和接口约定。
3. **代码实现（`implementation`）**：在限定仓库、分支和文件范围内产出代码变更。
4. **自动化测试（`test-suite`）**：执行测试并保存测试证据。
5. **安全审查（`security-review`）**：审查依赖、秘密、权限和已知漏洞。
6. **发布审批（`release-approval`）**：人工查看证据、风险和变更摘要后批准或拒绝。
7. **部署（`deployment`）**：在目标环境执行部署；真实部署需由受控的部署 Worker 执行，不应直接由浏览器触发 shell 命令。

每个节点的定义不应只写“调用某某 Agent”。还应该写清楚：`dependsOn`、`executionMode`、输入与输出 Schema、超时、最大尝试次数、可重试错误类别、所需证据、幂等要求，以及需要人工审批的动作。

例如，部署节点可以有这样的约束：

```json
{
  "id": "deployment",
  "executionMode": "system",
  "dependsOn": ["release-approval"],
  "maxAttempts": 2,
  "retryableErrorClasses": ["transient_network_error", "worker_lost"],
  "requiresEvidence": ["release-manifest", "approval-record"],
  "requiresIdempotencyKey": true,
  "sideEffect": "external",
  "compensation": "rollback-deployment"
}
```

这段配置不是完整生产规范，但已说明重要差异：部署是对外部系统的副作用；它要有幂等键，要验证审批记录，并且要明确回滚或补偿策略。**重试并不等于重新来一遍；对有副作用的操作，首先要想清楚重复执行是否安全。**

## 四、重试、失败、超时与补偿：不要把它们统称为“再跑一次”

失败恢复是工作流设计最容易留下隐患的地方。

### 4.1 按错误类别做决策

我们可以把错误分为四类：

1. **瞬时错误**：网络断连、服务限流、Worker 短暂退出。通常可以按策略退避重试。
2. **输入或逻辑错误**：必填字段缺失、测试断言失败、Schema 校验未通过。再次执行相同输入一般不会自动修复，需要回到上游修改。
3. **权限或策略拒绝**：越权工具调用、审批未通过、违反客户数据隔离策略。不可自动重试来“碰碰运气”。
4. **未知错误**：缺乏明确分类的异常。应有限次重试或直接升级人工处理，不能无限运行。

行业工作流引擎通常将重试策略和错误分支作为显式定义。例如 AWS Step Functions 提供 `Retry` 和 `Catch` 机制，允许在一定尝试次数后转入补救路径；Temporal 把不可靠的外部操作放在 Activity 一类的执行单元中，并以策略控制重试、超时和心跳。这些是值得借鉴的工程模式，而不是要求每个软件工厂必须采用某一个供应商。

### 4.2 指数退避只是起点

一个常见的退避计算是：

\[
 d_n = \min(d_{max}, d_0 \cdot 2^{n-1}) + jitter
\]

其中 `d0` 是初始等待时间，`n` 是尝试编号，`dmax` 是等待上限，`jitter` 是随机抖动。抖动用于避免大量任务在同一时刻重试形成新的流量尖峰。

但策略更重要的几个字段是：

- 最大尝试次数（把“无限重试”排除在默认配置之外）；
- 错误可重试性（区分瞬时错误和确定性错误）；
- 超时与心跳（避免节点永久悬挂）；
- 幂等键或去重键（避免重试重复写数据、开资源、发消息或部署）；
- 失败后的路由（停止、跳过、人工介入、补偿或回滚）；
- 每次尝试的输入摘要、输出引用和错误信息。

### 4.3 补偿不是时间倒流

如果流程已经创建云资源、推送软件包或修改外部系统，失败后不能简单地把数据库状态改回去。应设计**补偿动作**，例如撤销发布、释放临时资源、恢复先前版本、将工单转回待处理状态。补偿也会失败，所以它本身必须有状态、有证据、有重试边界，必要时升级人工处置。

在 MVP 中，我们只把补偿策略记入定义，不执行真实回滚；真实系统要把部署和补偿动作放到独立的、权限受控的 Worker 中。

## 五、为什么这一篇值得配一套用户界面？值得，而且不是为了好看

当工作流只有一两个节点时，日志也许够用；当它拥有多个 Agent、多个分支、重试和审批时，单靠终端日志几乎不可能高效治理。**控制台是运行事实的可视化与受控操作入口，不是给 Agent 套一层聊天窗口。**

MVP 控制台至少包含以下视图：

### 5.1 运行列表：回答“哪些工作正在发生？”

按状态展示所有运行，支持搜索/筛选、查看创建时间、当前节点、持续时长和失败原因。状态汇总要来自运行存储，而不是浏览器自己猜测。运行 ID 应稳定可复制，便于日志、告警和工单引用。

### 5.2 节点时间线：回答“流程走到哪里？”

可视化呈现节点依赖、已完成节点、当前执行节点、审批门和失败节点。用户不仅要看见绿色/红色标签，还要理解前后依赖及当前节点为什么可执行。

第一版可以用按顺序排列的节点卡片来展示 DAG 的一个具体运行实例；等支持复杂并行分支后，再引入可拖拽的流程画布。不要一开始就开发一个只能画图、却没有真实状态同步的“流程设计器”。

### 5.3 节点详情：回答“这个结果凭什么可信？”

点开节点后展示：Agent 角色、Skill 版本、输入摘要、输出对象引用、开始与结束时间、尝试次数、错误分类、证据列表和策略判定。大段模型原始推理不应作为审计依据；应记录可验证产物、结构化结论和必要的操作摘要。

### 5.4 审批队列：回答“现在需要谁做决定？”

审批视图应让人看到变更摘要、测试结果、安全结果、目标环境、影响范围、回滚计划与风险，再做批准或拒绝。操作时必须附带操作人、时间和理由；审批意见要绑定具体运行与具体版本，不能变成脱离上下文的一个布尔值 `approved=true`。

### 5.5 运行控制：回答“出现异常时我能安全地做什么？”

控制台需要提供暂停、恢复、取消、重试等操作，但必须满足后端守卫条件。按钮被点击只是命令请求；后端返回成功后，界面才刷新状态。对于不可重试的失败，不显示可执行的“重试”按钮；对于生产部署，不允许 UI 跳过发布审批直接调用部署工具。

### 5.6 事件与证据：回答“谁在何时做了什么？”

事件时间线记录 `run.created`、`step.started`、`step.succeeded`、`step.failed`、`step.retry_requested`、`approval.granted` 等事实。事件应结构化、可检索，并关联到具体运行和节点。生产环境还应记录 trace ID、模型/提示版本、成本和耗时，但要遵守敏感信息最小化原则。

**实现建议：先做“运行控制台”，后做“流程设计器”。** 流程设计器解决定义的创作；运行控制台解决正在发生的事实与恢复决策。对于第一版软件工厂，后者通常更能帮助工程团队验证生产治理能力。

### 6.1 快速运行

需要 Python 3.11 或更高版本。这个演示控制台仅使用 Python 标准库，不需要安装前端框架或数据库服务：

```bash
python scripts/validate_workflow_definition.py
python -m unittest discover -s tests -v
python scripts/run_workflow_console.py --host 127.0.0.1 --port 8765
```

浏览器打开 `http://127.0.0.1:8765`。控制台会展示示例运行，可以新建演示运行、推进当前节点、模拟节点失败、重试、批准/拒绝审批、暂停、恢复和取消。

SQLite 文件默认保存在 `data/workflow_console.sqlite3`。演示数据只在数据库首次为空时初始化，操作记录会跨服务重启保留。若要重置演示数据，请先停止服务，再删除该 SQLite 文件。

### 6.2 这一版到底实现了什么？还没有实现什么？

**已实现：** 可校验的工作流定义、DAG 依赖检查、运行与节点状态、关键守卫条件、带事件记录的状态更新、SQLite 持久化、并发版本冲突检测、可操作的本地控制台和自动化测试。

**尚未实现：** 真实 LLM Agent 执行、后台任务队列/Worker、分布式调度、定时器与超时扫描、实时推送、企业身份认证、生产 RBAC、Secrets 管理、真实 CI/CD、真实部署/回滚、租户隔离、分布式锁与高可用数据库。

这条边界必须说清楚。一个操作台原型能验证数据模型和操作闭环，但不等于它已经具备生产级分布式执行保证。真实系统应将 API 命令、持久化状态、事件发布和 Worker 调度通过可靠的事务型发件箱（Transactional Outbox）或同等机制连接起来，并引入独立的执行器与身份授权。

## 七、把工作流本体与执行基础设施分层

当流程复杂起来时，一个常见错误是让本体负责所有调度细节，或反过来把语义和治理信息全部塞进任务队列。更清晰的分层是：

1. **领域本体层：** 定义需求、代码产物、测试证据、漏洞、审批、发布版本等业务语义及约束。
2. **工作流定义层：** 定义节点、依赖、条件分支、审批门、错误路由和策略引用。
3. **运行时编排层：** 执行状态机、保证状态转换、推进节点、计数尝试和处理恢复。
4. **执行器层：** 运行 Agent、Skill、测试命令、扫描任务或受控部署工具。
5. **存储与观测层：** 保存运行、事件、证据引用、审计、耗时、成本与追踪信息。
6. **控制台层：** 以权限受控方式展示运行事实，提交操作命令，审阅证据。

本体提供“对象是什么意思，什么关系合法”；状态机决定“这一刻允许什么转移”；Worker 负责“具体执行动作”；控制台负责“人如何看见和治理”。这几层紧密协作，但不能相互代替。

## 八、接入现有软件工厂仓库的建议

本篇的补丁是增量文件，不覆盖上一章的 Agent/Skill 契约。合并时建议按以下顺序：

1. 先合并 `workflows/` 和 `docs/`，检查节点 ID 与已有 Agent 角色、Skill ID 是否一致。
2. 再合并 `workflow_engine.py` 与 `workflow_store.py`，不要覆盖已有的 `__init__.py`。
3. 合并控制台与脚本后运行定义校验和所有测试。
4. 将真实执行接入独立的 Worker 接口，不要把工具调用直接塞到 HTTP 请求处理函数里。
5. 后续再把现有 Agent Task/Result Contract 与 Workflow Step 的输入输出 Schema 绑定起来；本篇只保留节点角色 ID 与产物证据槽位，避免再次定义一套冲突的 Agent 契约。

真实仓库若使用 Poetry、uv、Make 或已有 API 框架，应把本篇脚本作为可选入口纳入原有开发流程，不要直接替换项目级配置文件。

## 九、上线之前，用这些问题验收

- 对一个没有依赖完成的节点，状态机是否拒绝启动？
- 对一个缺少必需证据的成功结果，状态机是否拒绝推进？
- 测试断言失败是否会被错误地当成可无限重试的瞬时故障？
- 人工拒绝是否留下操作者、时间、理由以及关联版本？
- 重试是否生成新的 attempt 和事件，而不是覆盖原始失败事实？
- 并发的审批与取消命令是否可能互相覆盖？
- 服务重启后，运行状态和事件记录是否仍然存在？
- 用户是否只能对有权限、且当前状态允许的运行发出命令？
- 能否通过产物引用找到测试报告、扫描报告、审批记录和发布摘要？
- 失败后是否明确选择重试、回退、补偿、终止或人工升级中的一种路径？

如果这些问题还没有答案，先不要把“全自动部署”作为产品卖点。软件工厂的自动化成熟度，不以 Agent 数量衡量，而以**过程可解释、状态可恢复、权限可治理、结果可验证**来衡量。

## 十、下一步：从单机演示走向可恢复的分布式执行

本篇已建立工作流定义、运行实例、状态机、事件日志和运行控制台的最小闭环。下一步应重点研究“执行器与可靠任务交付”：如何把 Agent 任务投递到 Worker、如何处理至少一次投递导致的重复执行、如何用幂等键控制副作用、如何通过事件总线和可观察性把一次软件交付追踪到底，以及如何在多个客户/项目之间隔离上下文和成本。

软件工厂的核心不只是让 Agent 自动工作，而是让这份自动工作能够**被证明、被暂停、被恢复、被审计，也能在证据不足时被明确拒绝**。

## 本轮架构补充：把本体发现纳入有界、可恢复的审查工作流

本体候选生成不是一个无状态的“问模型一次”操作，而是有多阶段依赖、成本、评测和审批要求的长任务。仓库新增 `workflows/definitions/ontology-discovery-review-v1.json`，把流程定义为：来源预检 → 术语发现 → 关系发现 → 约束与能力问题发现 → 独立 Critic → 确定性校验 → 标注集评测 → 人工领域评审 → 生成版本化变更提案。

术语和关系发现之间存在依赖；不同来源的术语候选可以在未来按批次并行，但合并前必须确定性去重并保留各自来源证据。Critic 不能和作者 Agent 完全共享同一份自评结论；验证失败时，系统可把有结构化错误的结果交回修订，但需设置最大循环次数、token/费用预算和截止时间。超过预算或多轮仍无法解决的候选转人工评审，禁止无限循环。

事件、重试与候选存储应当分离。候选保存采用不覆盖策略；每一轮修订生成新的候选版本或差异记录。审批时绑定 `candidateDigest`；若候选内容变化，旧审批立即失效。外部模型超时后结果未知时，应查询/记录请求状态或以新的幂等执行键重试，不能因为没有收到响应就假定没有产生费用或调用。

当前代码已提供发现审查工作流定义与配置校验，并有本地 CLI 四阶段候选生成；该工作流尚未完全连到生产级分布式 Workflow Engine，所以“定义通过”不能视为整条工作流已在多 Worker 环境运行。验收时应分开检查工作流 DAG、各阶段运行测试和真实执行记录。
