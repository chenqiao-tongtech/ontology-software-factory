## 01 为什么代码仓库里有了组件，还不等于有了软件资产库？

一个团队可能已经有代码仓库、容器镜像仓库、部署模板、测试用例和运维文档。可是，当新的客户项目到来时，工程师仍然需要反复回答一组看似简单、实际很难回答的问题：

- 这个产品由哪些组件组成？每个组件当前批准使用哪个版本？
- 某个版本来自哪里，使用什么许可证，是否已经完成许可证审核？
- 一个组件依赖哪些其他组件？依赖的是版本范围，还是已经解析并锁定的确切版本？
- 两个组件的组合究竟经过验证，还是只是“看起来版本兼容”？
- 客户 A 的部署配置和补丁能否被客户 B 复用？标准版本升级后，哪些客户配置会受影响？
- 交付包中的二进制、SBOM、测试报告和来源证明，是否指向同一次真实构建？

如果这些信息散落在 README、微信群、表格、CI 日志和个人经验里，团队即使拥有很多“组件”，仍然很难稳定地重复交付。

**软件工厂需要的不只是代码仓库，而是一个能说清楚“我们有什么资产、它们之间是什么关系、哪些版本可以用、凭什么认为它们可以用”的资产目录。**

这里说的目录不是要取代 Git、制品仓库或漏洞扫描器。它的职责是把这些现有系统的记录连接起来，形成一份统一的、机器可检查的资产视图。

## 02 先把六类东西分清：产品、组件、版本、制品、客户配置和补丁

如果把所有东西都统称为“软件包”，后续的版本治理、权限控制和发布门禁很快就会混乱。本篇先采用下面这套最小分类。

| 对象 | 它回答的问题 | 示例 |
|---|---|---|
| 产品 Product | 最终交付给用户的产品是什么？ | 事件平台交付产品 |
| 组件 Component | 产品由哪些可复用部分组成？ | 中间件、扩展、部署模板、基础镜像 |
| 版本 Version | 具体引用的是哪个不可含糊的版本？ | `3.8.0`，以及对应的稳定版本 ID |
| 制品 Artifact | 实际可存储、分发和验证的文件是什么？ | 二进制包、镜像、配置包、SBOM、测试报告 |
| 客户配置 Customer Configuration | 某个客户如何在标准基线上覆盖非敏感参数？ | 副本数、资源规格、存储类型 |
| 客户补丁 Custom Patch | 为某个客户维护的代码差异是什么？ | 特定客户的兼容性补丁或定制适配 |

这些对象不是一一对应关系。一个产品通常包含多个组件；一个组件拥有多个版本；某个版本可能对应多个制品；一个产品版本还可能被不同客户的配置覆盖，但它们仍应指向相同的标准基线。

## 03 资产目录应当记录什么？

一个可落地的资产目录，至少应当为每个资产记录以下几个方面。

### 3.1 身份与责任人

每个产品、组件、版本和制品都需要稳定 ID。显示名称可以调整，稳定 ID 不应该随名称变化而改变。资产还需要明确责任团队、生命周期状态，以及谁可以批准它进入可复用目录。

例如：

```json
{
  "id": "sf:component:event-broker",
  "name": "示例事件中间件",
  "kind": "middleware",
  "owner": "platform-team",
  "lifecycleStatus": "active"
}
```

这里的 `active` 只是目录中的生命周期状态，**不代表该组件的每个版本都已通过测试、安全审核或生产发布审批**。资产可被发现，与资产可用于某次发布，是两个不同判断。

### 3.2 来源、版本和内容摘要

对于每个组件版本，应记录来源地址、不可含糊的 source revision，以及实际制品的内容摘要（digest）。标签如 `latest` 可以方便人浏览，却不适合作为部署与审计的唯一标识，因为同一个标签可能在不同时刻指向不同内容。

版本约定可以参考 [Semantic Versioning 2.0.0](https://semver.org/lang/zh-CN/spec/v2.0.0.html)。但需要注意：SemVer 是版本号表达与变更兼容预期的约定，不是兼容性测试本身。版本号符合 `3.8.0` 的格式，并不能证明它适合某个运行时、某个插件或某份客户配置。

### 3.3 许可证不是一个标签就算完成合规

目录可以记录 SPDX 风格的许可证标识、审核状态、审核人、时间和适用义务。真正的许可判断还可能受到实际分发方式、修改方式、捆绑依赖和合同条件影响。

因此，推荐把这两件事分开：

1. **声明信息：** 组件元数据声称的许可证标识是什么。
2. **审核结论：** 组织是否针对目标版本和使用方式完成了审核，并允许在特定用途下复用。

本篇示例校验器要求处于 `active` 状态的组件具有 `reviewStatus: approved`。这是本项目的 MVP 治理规则，不是对所有软件项目都适用的通用法律结论。示例中的许可证记录也只是合成数据，正式项目必须基于真实来源审核。

### 3.4 依赖必须同时记录“声明范围”和“最终解析版本”

依赖描述中常常有两个不同的问题：

- 声明：项目允许哪些版本？例如 `>=3.8.0,<4.0.0`。
- 解析：这一次实际交付使用了哪个具体版本？例如 `3.8.0`，并用稳定 ID 指向该版本记录。

因此目录中的依赖同时保留 `versionConstraint` 和 `resolvedVersionId`。前者说明允许范围，后者说明本次被锁定的目标。两者缺一不可：只记约束，构建结果可能随时间改变；只记版本，又很难知道它是否符合原始依赖声明。

当前代码实现了一个**有明确范围的 SemVer 子集**：精确版本、`^`、`~` 和逗号分隔的比较条件。它还不是 Maven、npm、Python 环境标记或容器平台约束的完整解析器。不同生态需要相应适配器，不能把这个小型实现冒充为通用依赖求解器。

### 3.5 兼容性是带证据的声明，不是从版本号推理出来的结论

目录中的兼容性记录应区分：

- `untested`：尚未测试，不得推断兼容或不兼容。
- `compatible`：有覆盖明确版本组合与运行条件的已验证证据。
- `incompatible`：有已验证证据表明该组合在所描述的条件下存在不兼容问题。

证据应该指向具体测试报告或其他记录，并尽可能包含运行平台、配置、测试套件版本、测试时间和源代码/构建标识。即使测试通过，也只能支持测试覆盖范围内的结论，不能自动推出对所有环境都兼容。

## 04 SBOM、来源证明和资产目录是什么关系？

在软件供应链中，几个术语容易混在一起。它们实际承担不同职责：

- **资产目录：** 管理组织认可的产品、组件、版本、所有权、生命周期、依赖锁定和客户配置关系。
- **SBOM（软件物料清单）：** 描述某个软件版本或制品包含哪些组件及依赖。可参考 [SPDX 规范](https://spdx.github.io/spdx-spec/) 或 [CycloneDX 规范概览](https://cyclonedx.org/specification/overview/)。CycloneDX 也提供组件、依赖关系、漏洞与许可证等供应链透明度建模能力。
- **来源证明（Build Provenance）：** 描述制品是在什么构建过程、源代码和依赖条件下产生的。可参考 [SLSA Build Provenance 规范](https://slsa.dev/spec/v1.1/provenance)。
- **测试与安全报告：** 记录具体工具在具体提交、构建和配置上实际执行后得到的结果。

资产目录应该**引用或汇总这些系统产生的证据**，而不是自己生成一段文字，就宣称 SBOM、来源证明或安全验证已经完成。

本篇代码包为每个资产制品记录 `uri`、`digest`、`verificationStatus`、来源类型等元数据，并给版本预留 `sbomArtifactId` 与 `provenanceArtifactId`。但示例里的 `artifact://demo/...`、摘要字符串和报告引用都是占位数据，状态标记为 `pending`；它们不对应真实文件，也不是有效的 SBOM 或 SLSA 证明。

这一区分非常重要：**字段存在，只代表目录里声明了一个证据引用；只有可信工具获取并校验真实内容，才可能支持实际的放行决策。**

## 05 标准资产、客户配置和定制补丁，必须分层管理

软件工厂的目标之一，是让标准能力跨客户重复使用，而不是每交付一个客户，就复制一份代码并在其中不断修改。

推荐采用三层结构。

### 第一层：标准产品与标准组件

管理通用版本、依赖关系、许可证审核、测试套件、制品与来源信息。这个层面的变更应该走统一的版本治理与质量门禁。

### 第二层：客户配置覆盖

客户环境的副本数、资源规格、域名、存储类型、可观测性选项等差异，尽量使用版本化的配置覆盖来表达。配置必须指向明确的产品与组件基线，使后续能比较两个客户到底改了什么。

**密钥不能放在普通配置覆盖里。** 目录只保存密钥管理服务中的引用，例如 `vault://customer-north/event-platform/sasl-password`，实际秘密由专门的密钥管理和授权系统控制。当前 MVP 会拒绝形如 `password`、`apiToken`、`privateKey` 的普通覆盖键。

### 第三层：客户专属代码补丁

当差异无法通过配置表达时，可建立一个独立的客户补丁对象，并记录：

- 所属客户与负责人；
- 修改的标准组件及其基线版本；
- 补丁仓库和精确提交；
- 补丁制品；
- 测试证据、安全审核状态和批准记录。

客户补丁不应该悄悄修改全局标准组件，也不应该被默认发布给其他客户。若后续发现它对多个客户都有价值，再按标准产品的流程评估是否回收成公共能力。

### 一个简化的客户配置示例

```json
{
  "id": "sf:customer-config:north-tenant-1",
  "tenantId": "customer-north",
  "productId": "sf:product:event-platform",
  "configurationVersion": "1.0.0",
  "status": "validated",
  "owner": "customer-delivery-team",
  "baseVersionIds": [
    "sf:version:event-broker-3.8.0",
    "sf:version:deployment-template-1.1.0"

  "overrides": [
    {"key": "replicaCount", "value": 3},
```

### 校验分为两个层次

**第一层是 JSON Schema 结构校验。** 它检查必填字段、类型、状态枚举、版本格式、摘要格式和不允许出现的额外字段。

**第二层是跨对象语义校验。** 它检查：

1. 目录中的 ID 是否重复；
2. 产品引用的组件是否存在；
3. 默认版本和依赖解析版本是否属于正确的组件；
4. 解析版本是否满足声明的 SemVer 约束；
5. 依赖图中是否出现循环；
6. 兼容性结论是否引用已验证的证据；
7. 客户配置是否只引用该产品包含的版本；
8. 客户补丁是否属于同一租户、是否关联正确的基线和制品；
9. 普通配置中是否混入密钥类字段。

这里依然要明确边界：**通过目录校验，不等于产品已经可以发布。** 这只是证明元数据结构与指定的引用规则一致。真正的放行还需要真实制品、许可证审核、SBOM、来源证明、测试和安全结果。

## 07 软件资产治理的常见陷阱与应对措施

| 风险 | 为什么会出问题 | 建议措施 |
|---|---|---|
| 使用 `latest` 作为唯一版本 | 同一引用在不同时间可能指向不同内容 | 固定版本、源修订和内容摘要，并保留依赖锁 |
| 把声明的许可证当成审批结论 | 元数据可能不完整，分发与修改方式也会影响义务 | 分离许可证标识与审核状态，设立责任人和审计记录 |
| 用版本号推断兼容 | 版本范围表达允许候选，不代表已通过真实组合测试 | 记录兼容性状态和证据；未测试必须明确标记 |
| 配置与代码补丁混在一起 | 客户分支难升级，公共资产难复用 | 先配置覆盖，必要时才建立租户专属补丁 |
| 客户密钥落到 JSON、日志或 Git | 造成凭证泄漏 | 只保留 Secret Manager 引用，执行日志做脱敏 |
| 目录中的摘要没有对应真实文件 | “有 digest”会被误解为“内容已验证” | 真实工具重算摘要，校验下载内容和可信来源 |
| SBOM / provenance 字段存在就认为合规 | 只填写链接并不等于文件有效或证据可信 | 检查真实文件、签名/证明、来源链与覆盖范围 |
| 依赖范围过宽或未固定 | 同一源码在不同时间可能解析出不同依赖 | 保留声明范围、解析版本和锁文件，构建时固定输入 |
| 客户补丁被误当作标准版本 | 其他客户可能无意中继承未评估变更 | 单独标注租户、基线版本、审批、测试和安全状态 |

## 08 从资产目录走向软件工厂

当资产信息变成机器可读结构后，后续 Agent 才有可能可靠地完成资产选择，而不是凭文本相似度猜测“这个版本应该能用”。

例如，架构 Agent 可以提出需要某个组件与目标运行环境；目录服务返回候选版本、依赖和兼容性证据；工作流再检查许可证审核、制品完整性和安全门禁。若缺少证据，系统应当返回“未知/需验证”，而不是让模型补出一个看似合理的结论。

不过，目录本身不应该被设计成一个全能决策引擎。它向流程提供可审计的事实和声明，真正的许可、授权、风险接受与发布决策仍由策略、责任人和可信工具执行。

**本篇的核心原则可以总结为一句话：可复用，不等于可以随意复用；版本明确，不等于已经验证；记录了证据，不等于证据已可信。**

下一篇我们将沿着同一个代码库继续前进：设计工厂里的 Agent 岗位，明确每个角色的职责、输入输出、Skills、上下文和工具权限，让多智能体可以基于同一套业务语义协作。

## 本轮架构补充：让资产目录成为本体发现的高价值输入

本体自动发现的质量很大程度取决于输入材料。对于软件工厂，不能只把几份自然语言需求交给 LLM；应优先收集**版本化、可定位、可核验的工程资产**：组件清单、依赖锁文件、API/JSON Schema、数据库 DDL、配置模板、兼容性声明、许可证文件、SBOM、构建清单和历史变更记录。

为每份来源统一记录 `sourceId`、`sourceType`、版本或提交 ID、定位符、所有者、许可/访问边界和 SHA-256。自动发现流水线把这些信息写入候选的 `sourceManifest`；每个术语、关系与约束再引用具体证据片段。这样能够区分“供应商声明支持某版本”“仓库里确实存在某个锁定依赖”和“我们自己运行测试验证过兼容”这三种不同证据等级。

NVIDIA Auto Ontology 的元数据目录可以作为一个可选输入适配器，用于读取外部语义目录中的术语或缩写元数据；但拉到一条目录记录，不等于验证它所描述的资产确实可下载、许可证可用或版本仍受支持。Cognee 可以在独立候选空间帮助组织文档与关系图，但不得将图上的推断直接覆盖产品资产目录。

资产目录和本体发现的职责应当保持分离：**资产目录回答“有什么、哪个版本、从哪里来、是否获批复用”；本体发现回答“这些对象可能代表什么、彼此怎样关联、还需要验证哪些业务问题”。** 在两个系统之间，只通过有版本的元数据契约和证据引用连接。

建议在资产变更时按需触发增量发现：上游组件版本、API Schema 或许可证发生变化时，重新分析受影响候选；没有变化的源材料可通过摘要缓存避免重复调用模型。对敏感客户代码，应先经过数据分类和发送策略；如果不能外发，就使用获准的本地模型或不发送该来源。

配套实现：`src/ontology_software_factory/adapters/nvidia_auto_ontology.py` 是可选只读目录适配器；`src/ontology_software_factory/adapters/cognee_ontology.py` 只负责候选图文档和评审暂存，不负责资产批准。外部服务尚未在本地验收环境实际连接，当前验证覆盖的是适配器契约和隔离规则。
