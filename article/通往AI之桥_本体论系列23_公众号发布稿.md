# 第 23 篇｜从标准产品到客户交付：版本发布、环境配置、升级与回滚

> 「通往AI之桥」·《本体论在 AI 工程中的实践》修订版 v2.0 · 软件工厂实战
>
> **本篇目标：** 只有质量门禁通过的候选产物才能生成版本化交付包；生成文件摘要清单与 CycloneDX 格式的配置包 SBOM；通过独立批准演练升级与回滚，并明确区分模拟状态和真实部署。

## 01 发布是一个可追溯的交付对象

生产系统需要的不是一个 ZIP 文件，而是一份版本化交付对象：需求和运行标识、资产版本、配置、构建记录、测试和安全证据、文件摘要、支持边界、目标环境及批准记录。客户配置和标准资产必须分层；不应因为一个客户的参数变化就复制和分叉整个标准产品。

本例只交付 Kafka 配置包，不包含 Kafka 二进制。`release_manager.py` 生成 release manifest，列出包内文件 SHA-256，并输出一个用于配置交付物自身的 CycloneDX 文件。SBOM 的组件描述的是这个配置交付包，不会把目录中占位的 Kafka artifact digest 伪装成真实被分发组件。

## 02 发布包的生成规则

```bash
python scripts/run_software_factory_pipeline.py \\
  --request examples/requests/kafka-development.json \\
  --output-root .local-runs --run-id release-demo
python scripts/run_quality_gate.py --run-dir .local-runs/release-demo
python scripts/create_release.py \\
  --run-dir .local-runs/release-demo \\
  --deliverables deliverables --release-id release-demo-001
```

如果质量报告不是 `passed`、`releaseAllowed` 不为真、run ID 不一致或制品摘要不一致，`create_release.py` 会拒绝打包。输出包括 `release-manifest.json`、`sbom.cdx.json`、质量报告、配置验证结果、构建记录以及 ZIP 交付包和外部发布记录。

## 03 用模拟环境验证升级和回滚

本篇提供 `scripts/rehearse_upgrade.py`，它只更新本地模拟环境的 JSON 状态文件，并要求填写独立审批人和审批原因。允许的目标只有 `test-simulation` 和 `staging-simulation`；指定 production 或其他外部环境会直接拒绝。

```bash
python scripts/rehearse_upgrade.py \\
  --state .local-environments/staging.json \\
  --release-record deliverables/release-demo-001.release-record.json \\
  --approved-by reviewer@example.invalid \\
  --reason "演示环境升级演练"
```

增加 `--simulate-health-failure` 可验证健康检查失败后恢复之前的状态。它证明回退状态机逻辑可运行，不证明真实 Kafka 服务、数据库迁移或 Kubernetes 集群已经成功升级/回滚。

## 04 生产部署仍需外部系统和授权

真实发布还需要制品仓库、签名/证明验证、部署适配器、变更窗口、环境健康检查、数据迁移预案和回滚策略。对于不可逆的数据迁移，不能简单地恢复配置文件就宣称完成回滚。生产变更必须由实际 IAM、审批系统和部署平台约束，本地状态机不能替代它们。

## 本轮架构补充：本体变更也需要版本化发布、兼容与回滚

LLM 提出的本体变更不能直接覆盖 `ontology/software-factory-ontology.json`。每项变更首先保存为独立 `OntologyCandidate`，再经过证据核验、Benchmark 评测、领域审核和差异检查。批准记录需要绑定候选内容摘要、评审人、时间和理由；候选摘要发生变化时必须重新审批。

批准后应生成一个版本化变更提案，而不是立即向生产语义注册表写入。变更清单需要列出受影响的 JSON Schema、语义校验器、Agent 输入输出、Skill、Workflow、Policy、工具契约、资产元数据和历史数据映射；随变更生成兼容性测试与迁移计划。删除或重命名核心概念时，必须声明弃用窗口、替代概念和迁移规则。

正式发布通过独立评审后再进入受版本控制的主分支/注册表。若下游回归失败，则回滚到上一已批准本体版本，并保留已生成业务对象的原始版本号，避免历史记录被无痕重解释。当前实现支持候选摘要、审批绑定和版本提案所需的元数据设计，但没有连接企业本体注册中心或生产发布平台；这里的发布流程仍是本地参考实现。


## 小结

版本化交付的关键是来源、证据和审批，而不是压缩文件本身。下一篇将把运行、质量、成本和审计信息汇总起来，并把异常反馈变成经过责任人审核的本体或工作流变更提案，而非自动修改规则。
