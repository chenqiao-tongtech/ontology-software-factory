# 第 24 篇｜让软件工厂持续进化：运行观测、成本核算、审计与本体生命周期运营

> 「通往AI之桥」·《本体论在 AI 工程中的实践》修订版 v2.0 · 软件工厂实战
>
> **本篇目标：** 建立按运行记录聚合的本地观测报告；将模型 Token、执行阶段、质量门禁、版本交付和人工回滚关联到可查询的证据；为本体/工作流变更提供可审批提案，不允许运行异常自动改写生产规则。

## 01 没有基线，无法证明 Agent 带来了收益

软件工厂不能只统计调用了多少次模型、运行了多少个 Agent。真正需要关注的是端到端交付成功率、质量门禁阻断率、人工介入和返工、交付时延、模型和工具成本，以及需求—配置—构建—测试—制品之间的追溯覆盖率。

应当将人工基线与自动化基线放在同样的任务集和质量条件下比较。Agent 数量增加不意味着效率自然增加；如果质量下降、重试增加或人工复核负担扩大，系统可能只是把工作从一个环节转移到了另一个环节。

## 02 本篇实现的观测报告

`src/ontology_software_factory/observability.py` 会读取运行目录中的 `run-record.json`、`quality-gate-report.json`，并可选读取 `llm-usage.jsonl` 汇总模型用量。

```bash
python scripts/report_factory_observability.py \\
  --runs-root .local-runs \\
  --rates observability/config/model-rates.example.json \\
  --out observability/reports/latest.json
```

报告包括运行数量、候选构建数量、失败/阻断数量、质量报告统计、追溯路径，以及可配置的模型用量成本。价格没有配置时，成本字段保留 `null` 并标记 `unknown_rate`；不会根据模型名称猜测当前价格。请把模型价格和执行资源单价配置为可审计、带生效日期的运营数据。

当前的本地参考版还不是多租户生产遥测平台：它没有部署 Prometheus/OpenTelemetry 后端、统一日志服务或财务系统集成。它提供的是明确的事件和报告格式，便于下一步连接真实观测系统。

## 03 从反馈到本体变更：先提案，再评审，再发布

运行数据可能提示：某类需求经常缺少验收标准；某个配置规则造成反复失败；某个资产兼容声明没有证据；某个 Skill 输出经常不符合契约。这些观察可以生成变更提案，但不能让 Agent 直接修改 `ontology/`、权限策略或生产工作流。

```bash
python scripts/propose_ontology_change.py \\
  --out ontology/change-proposals/proposal-demo.json \\
  --run-id release-demo \\
  --problem "兼容性规则缺少测试证据链接" \\
  --proposal "为兼容性声明增加必需 evidence reference" \\
  --asset ontology/software-factory-ontology.json \\
  --owner domain-owner
```

提案带有责任人、来源运行、影响对象、必需证据、待审状态和 `automaticMutationPerformed=false`。正式变更应经过影响分析、回归测试、领域专家/产品负责人和安全责任人评审，再版本化发布。

## 04 指标与成本规则

- **成功率：** 需清楚区分“候选包构建成功”与“客户交付成功”。
- **质量阻断率：** 反映输入质量、策略严格度和潜在风险，不应简单追求越低越好。
- **成本：** 模型调用、重试、工具运行、执行环境、人工复核与返工需一起核算。
- **追溯覆盖率：** 需求、资产版本、运行 ID、校验日志、构建记录、制品摘要和审批应能连成链。
- **生命周期：** 本体、Skill、工具、工作流、质量策略都需要所有者、版本、兼容性、弃用和回归测试策略。

## 本轮架构补充：用运营数据驱动本体演进，而不是让模型自行“持续学习并修改生产定义”

本体生命周期运营需要持续记录候选与最终审核结果：各数据源贡献了多少有效术语、关系证据覆盖率、重复率、关系端点错误、Critic blocker 率、候选接受/拒绝比例、人工评审耗时、每个被接受候选的模型成本，以及变更后下游测试是否回归失败。这些指标能够帮助判断自动发现有没有降低建模成本，而不是只看 Agent 调用次数。

当出现新产品版本、API Schema 变化、构建失败模式、新术语或客户反馈时，可以触发增量发现任务。但重新发现应与正式本体隔离；先比较候选与当前版本的语义差异，再由本体责任人决定接受、拒绝或延后。对同一源材料和模型配置，可以利用 SHA-256 与调用缓存避免无效重复；更换模型、提示模板或阈值后则要重新评测，避免把版本漂移误认为业务变化。

建议观测链至少关联：`sourceManifest`、`candidateDigest`、`model/provider`、提示与 Skill 版本、token/延迟/成本、评测结果、审核决定、正式本体版本，以及相关 Workflow/Release 的 ID。涉及受限客户材料时只记录经批准的元数据或脱敏引用，不把原文内容写入公共观测日志。

**运营闭环应当是“反馈 → 候选 → 评测 → 人工评审 → 版本发布 → 下游回归 → 继续观测”。** 不是“反馈 → LLM 自动改写正式本体”。当前本地报告和候选评估器提供了开始运营度量的基础；真实费用核算、生产数据接入和自动化漂移监测仍需按部署环境补齐。


## 小结

本体驱动的软件工厂不是会自我改写规则的黑箱。可靠的持续进化依赖明确指标、可追溯证据、责任人和版本治理。到这里，v2.0 的第 15～24 篇正式主线形成了从范围和语义建模、工具接入、流水线执行、质量门禁、发布演练到运营观测的第一版可运行闭环；仍未接入的外部服务和生产设施必须继续保留为明确的验收缺口。
