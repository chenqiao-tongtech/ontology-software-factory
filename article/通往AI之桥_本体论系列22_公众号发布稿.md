# 第 22 篇｜质量与安全门禁：让不合格产物不能悄悄进入发布阶段

> 「通往AI之桥」·《本体论在 AI 工程中的实践》修订版 v2.0 · 软件工厂实战
>
> **本篇目标：** 将结构校验、资产目录一致性、秘密模式扫描、制品摘要验证与许可证复核元数据纳入机器可执行门禁；对生产候选要求外部扫描证据，缺失时 fail closed。

## 01 门禁的职责不是生成一份漂亮报告

质量门禁要回答可判定的问题：必需配置是否完整？候选制品摘要是否与构建记录一致？是否有疑似密钥？被选资产是否在目录中且版本明确？许可复核元数据是否存在？生产规则要求的扫描器是否实际执行并有证据？

报告只有在关联到具体运行、输入配置和制品摘要时才有意义。模型的“安全审查通过”可以作为辅助意见，但不能替代扫描器和确定性规则的实际结果。

## 02 本篇实现的门禁规则

`src/ontology_software_factory/quality_gate.py` 会生成 `evidence/quality-gate-report.json`。当前包括：

- 配置结构校验结果；
- 资产目录结构和关系校验；
- 配置包摘要与 `build-record.json` 的一致性；
- 配置中的凭据样式字符串扫描；
- 活跃资产许可证复核元数据检查；
- `trivy`、`gitleaks` 等外部扫描工具是否安装、是否执行以及是否为当前目标环境必需。

状态分为 `passed`、`blocked` 和 `incomplete`。关键检查失败时 `blocked`；必要外部扫描缺失时不能进入 `passed`。开发环境可能允许某些外部扫描器 `not_run`，但这会保留警告；生产配置默认要求相应扫描证据，因此当前没有工具执行证据时会被阻断。

## 03 为什么不能把“工具没有安装”算成“没有漏洞”

扫描未运行与扫描通过是完全不同的状态。本例的交付物是配置包，不包含 Kafka runtime 二进制，因而不应该伪造容器扫描或真实依赖漏洞报告。对生产配置包，策略要求 Trivy 与 Gitleaks 实际执行；如果本机没有安装，报告会将必需扫描器标为 `incomplete`（并记录未安装的路径状态），门禁拒绝放行。安装后代码会使用固定参数实际启动扫描器，保存报告与日志摘要；扫描器报高危发现时门禁为 `blocked`，超时或报告不完整时仍为 `incomplete`。

对后续生成源代码的任务，还需要接入 SAST、完整 SCA、秘密扫描、许可证扫描，并将报告绑定到 commit SHA、build ID 和 artifact digest。当前内置秘密模式扫描仅针对示例配置文件，不应宣传成全仓库秘密检测产品。

## 04 验收：正向和负向都要测

```bash
PYTHONPATH=src python -m unittest tests.test_quality_gate -v
python scripts/run_software_factory_pipeline.py --request examples/requests/kafka-development.json --output-root .local-runs --run-id gate-dev
python scripts/run_quality_gate.py --run-dir .local-runs/gate-dev
```

生产目标示例：

```bash
python scripts/run_software_factory_pipeline.py --request examples/requests/kafka-production.json --output-root .local-runs --run-id gate-prod
python scripts/run_quality_gate.py --run-dir .local-runs/gate-prod
```

若没有必需外部扫描器的执行证据，生产 Gate 应非零退出并保持 `releaseAllowed=false`。测试还会故意篡改制品摘要、注入凭据样式内容，确认门禁阻断。

## 本轮架构补充：给本体发现建立独立质量门禁

本体候选也需要质量门禁，但门禁指标不能只有“JSON 能解析”或“模型生成了多少概念”。新增评测器支持与人工标注 Benchmark 做精确匹配，计算术语 Precision/Recall/F1、关系 Precision/Recall/F1 和来源证据覆盖率；确定性校验还会检查来源片段可核实性、关系端点、重复候选与 Critic 的 blocker 发现。

建议首版门禁至少包括：

- Schema 与领域内部一致性校验通过；
- 必须有来源引用的概念和关系，其证据片段可在输入材料里找到；
- 核心术语与关系的评测指标达到项目设定阈值；
- Critic 不存在未关闭的 blocker/error；
- 关键能力问题已覆盖，或明确记录为待解决问题；
- 候选有固定摘要、模型/提示版本、源材料版本与评测结果。

阈值应通过标注集校准，不应把示例 Benchmark 上的 1.0 F1 当成真实质量证明。当前演示响应是固定 Fixture；其高分只证明评测器和样例相符。真实评测应由领域专家标注多类型来源、困难负例和跨版本样例，并报告样本数、分领域结果及人工复核一致性。

本体发现质量门禁与软件发布门禁也不能混淆：候选本体评测通过，只表示它可以进入人工语义评审，不代表可以直接发布正式本体或允许某个生产动作。发布仍要求独立授权、差异审核和下游回归。


## 小结

质量门禁必须依赖实际工具输出和可复核证据，而非自然语言承诺。下一篇将把通过门禁的候选包整理为版本化交付物，设计发布清单、审批和可重复的升级/回滚演练。
