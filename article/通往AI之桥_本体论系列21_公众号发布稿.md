# 第 21 篇｜从需求到真实产物：实现第一条可运行的 AI 软件生产流水线

> 「通往AI之桥」·《本体论在 AI 工程中的实践》修订版 v2.0 · 软件工厂实战
>
> **本篇目标：** 把结构化需求、批准资产选择、客户化配置、受控校验器、真实执行日志与制品摘要连接起来，完成第一条可重复运行的配置交付流水线。

## 01 “生成了一段文本”与“产出了制品”之间差了什么

一个 Agent 可以生成配置文件，却不能因此宣称配置有效。真实生产流水线至少要把需求保存为结构化对象，选择明确版本的批准资产，生成候选文件，运行实际工具，记录退出码和日志，生成可验证摘要，并把它们关联到同一运行 ID。

本系列以 Kafka 作为标准中间件示例，但目标不是从零重写 Kafka，也不是在本地假装构建了 Kafka 二进制。本篇实现的是：围绕目录中的示例资产，生成和验证一个**仅包含配置的交付包**。目录中的上游摘要目前是合成占位值，不能当作真实 Kafka 制品来源证明。

## 02 流水线如何工作

1. 读取 `contracts/schemas/production-request.schema.json` 并校验需求输入。
2. 从 `catalog/examples/demo-catalog.json` 选择处于 active 状态的示例组件和默认版本，检查许可证复核元数据。
3. 根据目标环境和受限覆盖参数渲染 `server.properties`。
4. 通过固定 Python 脚本、固定参数、`shell=False` 和有限超时，真实运行配置校验器。
5. 保存标准输出日志、退出码、耗时、日志摘要和配置摘要。
6. 将配置文件打包为 `candidate-config-bundle.tar.gz`，生成 `build-record.json` 和 `run-record.json`。完整仓库回归测试由 `make test` 单独运行，流水线内只运行针对本次候选文件的固定测试工具。

## 03 运行一条流水线

```bash
PYTHONPATH=src python scripts/run_software_factory_pipeline.py \\
  --request examples/requests/kafka-development.json \\
  --output-root .local-runs \\
  --run-id demo-kafka-001
```

结果保存在 `.local-runs/demo-kafka-001/`：

```text
candidate/server.properties
candidate-config-bundle.tar.gz
logs/config-validation.log
evidence/config-validation.json
evidence/candidate-tests.json
evidence/candidate-test-execution.json
evidence/build-record.json
run-record.json
```

`build-record.json` 记录资产和版本引用、配置哈希、制品哈希、文件大小及范围限定。运行状态是 `candidate_built`，且 `releaseEligible` 为 `false`。这意味着配置包已通过本地确定性校验并完成打包，但尚未通过第 22 篇的完整质量安全门禁，也没有部署到真实 Kafka 集群。

## 04 真实执行与安全边界

流水线不是让模型输出一条 Shell 命令再执行。它只运行仓库中明确指定的校验器脚本，并使用固定参数。输入中的目标环境只允许 `development` 或 `production`，可覆盖的字段有明确类型和上下限。请求中的任意路径不会被当成要执行的程序。

但这仍然不是内核级沙箱：执行器与 Python 进程运行于当前宿主机权限下。生产版应将任务放入临时容器或微虚机，限制 CPU、内存、文件系统和网络；在没有这些设施之前，不能将此执行器称为生产安全沙箱。

## 本轮架构补充：本体发现应服务于真实生产流水线，而不是成为孤立的知识实验

在生产线中，本体候选的价值是帮助澄清需求对象、资产关系、兼容约束和验证问题。它应作为一个**受控的前置分析工序**，先产出候选术语和约束建议，再由已批准的领域模型、资产目录和验收条件指导后续配置生成、构建与测试；不能在同一次运行中让 LLM 新造一条约束，再把该约束当作已经批准的质量门禁。

推荐的链路是：来源预检 → 本体候选 → Critic 与 Schema/语义验证 → 人工批准或记录为未解决问题 → 生成结构化 Requirement/ChangePlan → 资产解析 → 配置/代码候选 → 真实工具验证 → 交付证据。生产任务应记录所用的正式本体版本，以及候选本体是否被批准、被拒绝或仅作为解释性建议。

本地快速演示：

```bash
make demo-ontology-discovery
python scripts/validate_ontology_candidate.py \
  .local-runs/ontology-candidates/ocand-b74c362627f66aed.json
```

示例源材料是合成的软件工厂需求说明，输出候选包含来源清单、术语、关系、约束、能力问题和模型调用轨迹。该命令验证候选生成与本地证据规则，不会调用 Git、修改正式本体或自动改变生产质量策略。真实软件生产流水线仍以实际构建、测试与扫描工具的结果为准。


## 小结

这条流水线首次把模型之外的确定性工具结果作为正式证据保存。下一篇将用独立质量门禁审查候选包，区分“校验通过”“扫描未运行”和“发现阻断问题”，避免不合格制品悄悄进入发布环节。
