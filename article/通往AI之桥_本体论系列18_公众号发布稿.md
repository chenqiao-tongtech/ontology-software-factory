建议阅读时间：约 15–20 分钟

## 01 不要先创建七个 Agent，先定义七个岗位

在前两篇，我们先明确了软件工厂边界，再建立了领域本体和资产目录。现在，如果我们开始创建多个 Agent，最容易发生的错误，是给它们分别写出“你是一个资深架构师”“你是一名优秀测试工程师”之类的系统提示词，然后让它们自由对话。

这样的系统演示起来很直观，但在真实软件生产中有几个隐患：

- 需求 Agent 可以把推测当作已确认的业务事实；
- 开发 Agent 可能认为代码生成成功就等于交付完成；
- 测试 Agent 可能没有真正运行测试，却引用开发 Agent 的文字结论；
- 安全 Agent 可能误以为自己可以关闭发现或豁免门禁；
- 发布 Agent 可能把“整理好发布清单”理解成“有权正式发布”；
- 运维 Agent 可能将“提出重启建议”越界成“直接执行重启”。

这些并不只是 Prompt 质量问题，而是系统责任、权限和状态没有被显式表达。

**因此，我们先定义岗位，再选择模型；先定义契约，再设计协作；先定义权限边界，再接入工具。**

本篇会为 `ontology-software-factory` 建立 7 个角色定义、7 个 Skills、统一工具目录、上下文策略，以及机器可验证的 Agent Task / Result 契约。当前代码会检查这些配置是否一致，但不会假装已经接入大模型并运行真正的 Agent。

## 02 软件工厂里的七个岗位

我们先用七个职责相对独立的岗位打通端到端交付链。它们不是七个必须同时运行的独立模型；在早期实现里，部分岗位可以由同一个模型或同一个执行服务承担，只要权限、输入输出契约和审计身份仍然清晰。

| Role | 核心责任 | 主要输出 | 默认不能做什么 |
|---|---|---|---|
| **需求分析 Agent** | 澄清目标、范围、假设和验收标准 | Requirement 与验收条件 | 不把猜测写成确认事实，不写代码、不部署 |
| **架构设计 Agent** | 在已批准需求和资产范围内设计方案 | 架构方案、ADR 草案、依赖建议 | 不自行批准架构决策或未经审核引入新依赖 |
| **开发实现 Agent** | 在隔离分支中完成受限代码修改 | 代码差异、Build 候选、变更说明 | 不合并受保护分支、不发布、不部署、不读秘密 |
| **测试验证 Agent** | 执行真实测试、关联构建并报告覆盖缺口 | TestRun 与测试证据 | 不修改被测代码来制造通过，不发布 |
| **安全审查 Agent** | 检查依赖、许可证、安全发现和来源证据 | Vulnerability 与安全报告 | 不自行关闭高危发现或豁免门禁 |
| **发布协调 Agent** | 汇总构建、测试与安全证据，整理发布候选 | Release candidate 与证据清单 | 只能请求审批，不能自己批准或执行部署 |
| **运维支持 Agent** | 分诊运行事件，提出诊断和处置建议 | Incident 更新、Runbook 草案 | 不直接重启生产、切流量或恢复数据 |

为什么把发布和运维也作为独立岗位？因为软件生产不是代码停止变化时就结束。交付前需要把证据与版本关联，交付后需要理解部署状态和事件反馈。反过来，这也不意味着发布 Agent 必须有发布权限，或运维 Agent 必须有生产命令权限。**责任范围与执行权限必须分开设计。**

## 03 Role、Skill、Tool 到底有什么不同？

这三个词经常在各种 Agent 框架中混用，但在工程模型中建议明确区分。

| 对象 | 回答的问题 | 软件工厂中的例子 |
|---|---|---|
| **Role（岗位）** | 谁负责这个任务，职责边界是什么？ | `test-agent` 负责测试验证 |
| **Skill（技能包）** | 如何完成一类可复用任务？ | `test-evidence-collection` 定义执行测试、保存报告和验收标准 |
| **Tool（工具）** | 运行时实际可以调用什么能力？ | `tests.run` 在隔离 runner 中执行测试 |
| **Policy（策略）** | 这次调用是否允许？ | 当前租户、仓库、分支和工具参数是否符合授权 |
| **Workflow（工作流）** | 何时调用、失败后走哪一步？ | 测试失败后生成修复任务，而不是继续发布 |

一个 Role 可以使用多个 Skills；一个 Skill 也可以供多个 Role 复用，但实际权限应是**当前 Role 的授权集合与 Skill 所需工具集合的交集**，而不是 Skill 文档写了什么就能调用什么。

例如，“测试证据收集”Skill 需要 `tests.run` 和 `test-report.write`。若某角色没有被授予这些工具，该 Skill 就不能在该角色下执行；正确做法是调整并审核角色权限，而不是由 Skill 悄悄扩权。

同样，`SKILL.md` 中写“不要执行生产部署”不能代替真正的工具网关限制。如果底层凭证允许它调用生产部署 API，提示词不构成可靠安全边界。

## 04 把 Role 定义成机器可验证的契约

每个 Agent 岗位至少应当有以下字段：

- `roleId`：稳定的岗位标识；显示名称可以调整，ID 不应随之改变。
- `inputEntityTypes` / `outputEntityTypes`：它能读取和产出哪些本体对象。
- `skillIds`：允许使用的可复用技能。
- `toolIds`：岗位所需的工具白名单。
- `allowedActions` / `forbiddenActions`：岗位业务动作范围与显式禁止项。
- `contextPolicy`：共享上下文、任务局部上下文、受限字段与租户边界。
- `handoffRequirements`：下游角色接收任务前必须具备的结果和证据。
- `escalationConditions`：何时阻断流程并升级给人或其他责任岗位。
- `humanApprovalRequiredFor`：哪些动作必须进入独立审批流程。

示意片段如下：

```json
{
  "roleId": "test-agent",
  "displayName": "测试验证 Agent",
  "inputEntityTypes": ["Requirement", "Component", "Version", "Build"],
  "outputEntityTypes": ["TestRun", "Artifact"],
  "skillIds": ["test-evidence-collection"],
  "toolIds": ["workspace.read", "tests.run", "artifacts.read", "test-report.write", "contract.validate"],
  "forbiddenActions": ["repository.write", "repository.merge.protected_branch", "production.deploy", "secrets.read.raw", "agent.approve_self"]
}
```

这是结构示意；工程包中提供了完整 JSON 定义，并由 JSON Schema 和跨文件校验器检查。**Role 配置只是一份声明，不能直接作为 IAM 权限授予。** 运行时仍然要根据当前用户身份、租户、项目、任务和策略决策重新鉴权。

## 05 Skills 应该像工程资产，而不是一段万能 Prompt

一个可维护的 Skill 不应只有一段自然语言说明。它至少需要版本、兼容岗位、输入输出类型、所需工具、验收标准、失败条件、上下文要求和副作用边界。

本篇为七个岗位分别准备了七个 Skills：

| Skill ID | 适用岗位 | 主要验收点 |
|---|---|---|
| `requirement-normalization` | 需求分析 | 验收标准有稳定 ID；未决事实标记待澄清 |
| `architecture-plan` | 架构设计 | 方案包含范围、假设、替代方案、依赖与风险 |
| `bounded-code-change` | 开发实现 | 只修改允许路径；给出 diff 与实际验证情况 |
| `test-evidence-collection` | 测试验证 | 结果关联真实运行 ID、退出码、构建和报告 |
| `dependency-security-review` | 安全审查 | 发现关联具体组件/版本/制品，区分已确认和待复核 |
| `release-readiness-check` | 发布协调 | 缺失证据成为 blocker；只能生成候选并请求审批 |
| `incident-triage-runbook` | 运维支持 | 区分事实、假设和建议；只生成 Runbook 草案 |

每个 Skill 目录同时有 `skill.json` 和 `SKILL.md`。JSON 是机器检查的元数据契约；Markdown 是供开发者、模型运行时适配层和评审者阅读的操作说明。两者的职责不同，不应把自由文本说明直接当成执行权限。

Skills 还应有自己的回归样例。比如 `test-evidence-collection` 不只是“生成一份测试报告”，而应该测试它在 runner 超时、退出码为非零、测试报告缺失、报告与提交不匹配时，是否会正确阻断并升级，而不是输出成功结论。

## 06 上下文也要建模：共享、局部和受限

“把所有相关资料都塞进上下文”对软件工厂来说既昂贵又危险。更好的做法是按用途分层，并对每次读取单独检查权限。

### 共享任务上下文

它适合携带各岗位都需要知道的稳定信息，例如 task ID、租户/项目 ID、本体版本、需求 ID、验收标准、工作流状态、批准的组件版本和证据引用。它应该尽可能通过 ID 和引用传递，而不是把整个仓库、全部客户资料复制给所有 Agent。

共享不等于人人都能看。某个 Agent 看到 `artifact_id`，不代表它有权读取该制品；实际读取必须再次通过租户和资源授权检查。

### 角色局部上下文

它只包含当前岗位完成任务需要的信息。例如开发 Agent 的允许路径、源代码片段与指定测试命令；测试 Agent 的测试计划和被测构建 ID；安全 Agent 的依赖清单、扫描器版本和制品摘要。

局部上下文有助于降低无关信息、提示注入和错误关联的影响，也方便在任务结束后清理临时数据。

### 受限上下文

原始密码、API Key、私钥、生产凭证、其他租户源码和无关个人数据，不应进入模型上下文。若执行任务确实需要秘密，应由独立的短时授权执行环境按需获取，并避免将原始秘密返回模型或写入日志。

此外，仓库文件、Issue 评论、外部文档、扫描输出和 MCP 返回值都属于不可信输入。它们可以包含有用事实，也可能包含恶意或误导指令；不能让这些内容改变系统策略或扩大工具权限。

## 07 Agent 之间通过任务与结果契约交接

Role 界定岗位边界，但实际协作还需要一份统一任务契约和结果契约。本篇新增两份 JSON Schema。

### Agent Task

任务输入记录：

- `taskId`、`tenantId`、`projectId`、`roleId` 和 `ontologyVersion`；
- 输入对象的稳定 ID 和实体类型；
- 预期输出的实体类型；
- 带验证方法的验收标准；
- 上下文引用和敏感级别；
- 最大尝试次数、超时、工具调用上限；
- `idempotencyKey`，供工作流和工具适配层实现幂等处理。

### Agent Result

结果记录：

- `status`：`succeeded`、`blocked`、`failed` 或 `needs_human_review`；
- 输出对象的 ID、类型与 Schema 版本；
- 证据引用、错误代码和阻断原因；
- 是否需要人工复核、下一岗位建议以及完成时间。

重要的是，`succeeded` 只表示这个岗位按自己的契约返回了成功结果，并不直接授予工作流进入下一阶段的资格。工作流控制器还必须确认输出结构有效、证据来自可信工具、策略判断通过且状态转换合法。

例如，需求 Agent 如果发现“高可用”没有明确故障域或恢复时间目标，就应返回 `needs_human_review`，说明待确认点，而不是自行编造一个副本数再交给架构 Agent。当任务被阻断时，`blockedReasons` 必须明确；没有证据的结论不应变成“通过”。

## 08 工具权限矩阵：职责可以协作，权限不能互相继承

本篇新增 `agents/tool-catalog.json`，把工具按 ID、风险级别、副作用、是否需要人工审批和 MVP 是否启用进行声明。Role 只能引用目录中存在且已启用的工具。

以下是当前参考实现的权限原则：

| 工具/动作 | 需求分析 | 架构设计 | 开发 | 测试 | 安全 | 发布协调 | 运维支持 |
|---|---|---|---|---|---|---|---|
| 读取需求/目录/文档 | 受限只读 | 受限只读 | 按项目只读 | 按项目只读 | 按项目只读 | 读取证据 | 读取运行信息 |
| 写架构草案 | — | 允许 | — | — | — | — | — |
| 修改任务分支 | — | — | 有界允许 | 禁止 | 禁止 | 禁止 | 禁止 |
| 运行测试/扫描 | — | — | 受限测试 | 受限测试 | 受限扫描 | 读取结果 | 读取监控 |
| 写测试/安全证据 | — | — | 禁止自报通过 | 只能引用真实 runner | 允许写发现 | 汇总引用 | 记录事件证据 |
| 生成发布候选 | — | — | — | — | — | 允许 | — |
| 请求人工审批 | 仅范围问题 | 架构基线 | 高风险变更 | 特定例外 | 风险豁免提交人审批 | 允许请求 | 高风险操作请求审批 |
| 合并受保护分支 | 禁止 | 禁止 | 禁止 | 禁止 | 禁止 | 禁止 | 禁止 |
| 生产部署 / 读取秘密明文 | 禁止 | 禁止 | 禁止 | 禁止 | 禁止 | 禁止 | 禁止 |

为什么发布协调 Agent 只能“请求审批”？因为产生候选和批准候选是职责分离。测试 Agent 不能把自己的测试结果当作发布批准；安全 Agent 不能自行豁免自己发现的高危问题；Agent 也不能批准自己发起的变更。

权限必须由工具网关或执行服务在实际调用时执行，记录调用主体、发起用户、任务 ID、资源范围、参数、策略决定和执行结果。角色配置只是输入，不是最终授权。

公开工程实践也强调将自动校验与人工审批组合起来：低风险且可逆的动作可以通过白名单和沙箱控制，而发布、删除、权限变更等高影响动作应在发生副作用的边界前进行独立审核。[OpenAI Guardrails and Human Review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)；[OWASP Agent and MCP Security Guidance](https://owasp.github.io/DevSecOpsGuideline/2-Process/2-2-Develop/2-2-5-AI-Agent-and-MCP-Security/)。

## 09 从需求到运维：用明确交接减少返工

建议的主流程是：

1. **需求分析**输出结构化需求和验收标准。如果业务约束含糊，先升级澄清。
2. **架构设计**依据已批准资产和需求输出方案、依赖与 ADR 草案，等待架构基线确认。
3. **开发实现**在隔离分支按批准范围修改代码，提交差异与执行记录。
4. **测试验证与安全审查**在依赖满足后可并行执行，但都必须绑定相同的源代码/构建版本并生成真实证据。
5. **发布协调**汇总证据。如果任何必要的测试、安全或兼容性证据缺失，输出阻断原因；如果齐全，则生成候选清单并提交独立审批。
6. **运维支持**在受控交付后读取授权范围内的监控与事件，形成可审查的原因分析和 Runbook 草案。

重点是每次交接都传递稳定 ID、输出契约、状态和证据引用，而不是只传一句“我已经完成了”。下游岗位在接手前应验证上游输出是否满足契约；如果输入不完整，必须返回明确错误或阻断，而不是自动补全缺失事实。

### 一个测试失败的例子

测试 Agent 运行真实测试后发现失败。正确的结果应带有 `TestRun` ID、执行器 run ID、退出码、失败用例和报告引用，并将状态设为 `failed`。工作流可以把修复任务交还开发 Agent，但不能把测试失败记录改写为成功，也不能因重试次数用完而跳过门禁。若失败来自需求歧义或环境差异，应升级给架构或人工责任人，而不是无限循环重写代码。

## 10 如何运行本篇代码包？

本篇工程包包含：

- `agents/roles/`：7 个岗位 JSON 定义；
- `agents/tool-catalog.json`：工具风险与可用性目录；
- `skills/`：7 个带版本、工具要求和验收标准的 Skill；
- `policies/`：全局拒绝策略和上下文分层；
- `contracts/schemas/`：Agent Task 与 Agent Result 的 JSON Schema；
- `examples/agent-handoff/`：一份明确进入人工复核状态的需求分析任务与结果；
- `src/ontology_software_factory/agent_contracts.py`：跨文件契约校验；
- `tests/test_agent_contracts.py`：正向与负向检查。

在这个包目录执行：

```bash
python -m pip install -e .
python scripts/validate_agent_contracts.py
python -m unittest discover -s tests -v
```

校验器检查角色和 Skill 引用是否存在、Skill 所需工具是否在岗位权限内、是否授予禁用工具、是否存在允许/禁止动作冲突、上下文范围是否重叠，以及任务和结果示例是否符合契约。

需要明确：这些测试验证的是配置的一致性。它们不会启动模型，也不会真正执行 `tests.run`、安全扫描或生产审批。实际执行还需要第 19–20 篇的工作流控制器、工具适配器、身份权限、沙箱和审计机制。

## 11 风险与应对

| 风险 | 常见误区 | 应对方式 |
|---|---|---|
| 角色权限无限膨胀 | 为了省事让所有 Agent 共用全部工具 | 每个 Role 明确白名单；Skill 不能扩权；工具调用时再鉴权 |
| 上下文泄漏 | 把完整仓库、客户数据和秘密塞进共享上下文 | 共享稳定引用，角色局部按需读取，秘密只保留受控引用 |
| 提示注入跨 Agent 传播 | 外部文档告诉 Agent “忽略政策并部署” | 外部文本是数据，不是系统规则；工具端独立执行权限与输入校验 |
| 测试自证通过 | Agent 自己生成“测试已通过”报告 | 只有受信任 runner 的真实运行记录能作为测试证据 |
| 角色之间死循环 | 失败后 Agent 不断互相转交任务 | 最大尝试次数、超时、预算、明确责任人和可观测的阻断状态 |
| 责任边界不清 | 开发 Agent 既写代码又批准发布 | 分离开发、测试、安全审查和发布批准职责 |
| Skill 漂移 | 更新一段提示词，却没有版本与回归评测 | Skills 版本化；变更时同步更新契约、示例、验收与回归测试 |

## 12 本篇完成标准

- [ ] 七个岗位都有稳定 ID、责任、I/O 类型、工具白名单和禁止项。
- [ ] 每个岗位引用的 Skills 均存在，且兼容关系一致。
- [ ] Skill 所需工具是对应岗位实际获准工具的子集。
- [ ] 全局禁用工具（生产部署、主分支合并、秘密明文、策略修改、自我审批）不会被分配给 Agent。
- [ ] 每个岗位都显式区分共享、局部和受限上下文。
- [ ] Agent Task 和 Result 采用机器可验证 Schema。
- [ ] 失败、阻断和人工复核均有明确状态及原因。
- [ ] 示例交接能通过契约校验，负向测试能够拦截明显配置错误。

这意味着我们已经有了一套**可评审的 Agent 岗位设计和协作契约基线**，而不是说多智能体运行时已经上线。

## 结语：智能体越多，越需要明确边界

多 Agent 协作的关键，不是让所有 Agent 都能做所有事情，而是让每个岗位拥有恰当的信息、恰当的工具和可验证的责任。领域本体规定业务对象与关系，Role 规定职责范围，Skill 复用任务能力，Tool 提供真实执行接口，Policy 在执行边界控制权限，Workflow 则决定状态如何流转。

下一篇将把这些岗位连接成明确的生产流程：设计工作流、任务状态机、依赖、重试、暂停和失败恢复，让软件工厂的生产顺序不再依赖 Agent 在对话里临时决定。

## 本轮架构补充：本体发现也必须进入多智能体团队，而不是交给单个“万能 Agent”

本体发现是一个需要不同能力互相制衡的任务，建议采用四类专业岗位：

| 角色 | 职责 | 不能独自决定的事项 |
|---|---|---|
| Ontology Discovery Agent | 从可信来源提出术语、关系、约束和能力问题 | 不能把候选写成正式本体、不能批准自己输出 |
| Ontology Critic Agent | 独立检查证据、重复、循环定义、关系端点和推断边界 | 不能仅凭语言判断替代确定性验证器 |
| Semantic Validator | 用 Schema、图关系和来源规则执行确定性检查 | 不负责判断所有业务定义是否正确 |
| Domain Owner / Human Reviewer | 判断术语是否符合业务、批准版本变更 | 审批必须绑定审查过的候选摘要和差异 |

团队协作的控制面仍是 Workflow/State Machine。Discovery Agent 提交 `OntologyCandidate`；Critic 返回 `OntologyCriticSummary`；确定性校验器生成机器结果；评测器计算指标；只有所有强制条件满足后，流程才进入人工评审。任何 Agent 都不能自行调用 `ontology.publish`，该动作在策略层默认禁止。

LLM 能力应最大化用在语义相似度归并、歧义解释、反例生成、能力问题提案、候选关系说明、影响范围摘要和评审意见整理；结构合法性、来源引用核验、ID 唯一性、关系端点存在性、版本摘要和审批人身份则交由程序与授权系统核验。采用更强模型做 Critic、较经济模型做术语初筛可以作为可配置策略，但必须通过同一评测集比较成本与质量，不能假定多模型必然更好。

这一设计延续本篇的核心原则：Role 定义职责，Skill 定义做法，Tool 执行动作，Policy 决定边界，多智能体拓扑定义协作关系，Workflow 决定何时推进。模型可协助解释和提出方案，不能给自己增加权限或批准自己的高风险结果。
