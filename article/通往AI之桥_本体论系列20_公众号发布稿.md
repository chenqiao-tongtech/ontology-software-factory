# 第 20 篇｜把工程工具接入生产线：MCP、API 适配层、身份权限与安全执行环境

> 「通往AI之桥」·《本体论在 AI 工程中的实践》修订版 v2.0 · 软件工厂实战
>
> **本篇目标：** 建立可审查的工具契约与 default-deny 工具注册表；通过受控适配层连接本地工具和 MCP stdio 服务；让工具身份、输入校验、副作用等级和人工审批成为可执行规则，而不是写在提示词里的愿望。

## 01 为什么 Agent 接上工具，不代表它已经能安全执行

一个软件工厂会使用代码仓库、构建工具、测试框架、漏洞扫描器、制品库、部署平台和项目管理系统。工具接入带来了能力，也引入了新的风险：工具可能读错租户的数据，参数可能绕过业务约束，Agent 可能在不应写入的地方写文件，或者把外部文档中的恶意指令当成执行要求。

MCP 解决的是客户端与工具服务之间的标准化交互问题；API 契约描述业务接口；IAM 决定调用者身份和授权；工厂自己的领域语义说明调用的对象、前置条件与副作用；运行时策略和隔离环境则限制实际行为。这些职责不能混为一谈。

## 02 工具契约必须先于工具调用

本篇新增 `tools/registry.json` 和 `policies/tool-permissions.json`。每个工具至少声明：

- 稳定的 `toolId` 和输入 JSON Schema；
- 风险等级、副作用类型和审批要求；
- 可调用角色与实际注册处理器；
- 固定超时和错误处理策略（由调用适配层进一步实现）。

运行时有效权限取三者交集：**角色声明 ∩ 平台策略 ∩ 当前进程实际注册的工具**。未定义或未注册的工具一律拒绝。模型不能通过返回一个工具名或传入 `command` 字符串来创建新执行能力。

## 03 MCP 是连接协议，不是授权结论

示例 `adapters/mcp_stdio.py` 实现了最小 JSON-RPC stdio 交互：初始化、列出工具、调用已允许的工具。服务器启动命令必须来自经过评审的管理员配置，不能由需求文本、模型输出或网页内容拼接得到。子进程只继承明确允许的环境变量，避免默认把 API Key 传给 MCP 服务器。

```python
from ontology_software_factory.adapters.mcp_stdio import MCPStdioClient

with MCPStdioClient(
    ["/approved/path/to/mcp-server"],
    cwd="/approved/workspace",
    env_allowlist=("PATH",),
) as client:
    client.start()
    tools = client.list_tools()
    result = client.call_tool(
        "search_docs", {"query": "approved config"},
        allowed_names={"search_docs", "read_doc"},
    )
```

以上是客户端示例，不代表已经接入某个真实企业服务。仓库中的测试使用本地 fixture server，验证协议交互与工具白名单，不访问外网。

## 04 从低风险工具开始，按副作用逐步开放

建议将工具至少分为只读、受限写入、受限执行、高影响操作四级。只读工具可以先接入；工作区写入必须限定到当前任务；执行工具必须使用固定任务 ID 和白名单，不接受自由 Shell；发布、删除、生产部署和权限变更则需独立审批以及服务端授权。

不要把 `shell=False` 或“命令白名单”误认为完整沙箱。它们可以减少命令注入风险，却不能单独阻止被允许的程序访问网络、读取同一操作系统用户的文件或耗尽资源。生产执行仍需容器/微虚机隔离、只读文件系统、资源配额、网络出口策略、短期凭证和审计。

## 本轮架构补充：接入本体发现工具时，保持只读优先与候选隔离

本体发现会读入需求文档、数据库 Schema、API 定义、仓库文档和外部语义目录，因此工具层需要比普通文本生成更加明确的边界。新增的 NVIDIA Auto Ontology 适配器默认只读取语义目录元数据（术语和缩写相关端点），通过 `NVIDIA_AUTO_ONTOLOGY_API_TOKEN` 读取凭据；不支持向该外部服务写入或假设某个“自动创建正式本体”的 API 一定存在。Cognee 适配器只将候选映射到独立 `ontology-candidate-review-*` 暂存区。

所有来源都应经过大小限制、格式验证、秘密检测和数据分类。发现提示中引用的文档内容被视为不可信数据，不能把文档中的指令当成系统指令。远程 HTTPS 请求需要限制目标主机、超时、响应体大小和重定向行为；API Token 从环境/密钥服务注入，不得进入日志、候选文本、LLM prompt 或 Git。客户隔离区材料不能与公共语义目录混合写入。

工具权限分为 `source.read`、`candidate.write`、`candidate.validate`、`candidate.evaluate`、`catalog.import.read` 和 `ontology.publish` 等不同动作。MVP 中发现 Agent 只允许读取批准的来源并写候选；Critic 允许读取候选并写评审结果；真正发布本体的动作属于独立权限边界，默认拒绝并要求责任人审批。

参考项目：NVIDIA Auto Ontology（https://github.com/NVIDIA/auto-ontology）和 Cognee（https://github.com/topoteretes/cognee）。当前适配器测试使用假 HTTP/假图后端来验证契约，尚未证明连接了用户部署的真实 NVIDIA Auto Ontology 或 Cognee 实例。


## 小结

软件工厂不应把“Agent 能调用工具”当作目标，而应让每次调用都有身份、契约、授权、边界和证据。下一篇，我们把受控工具连接到一条实际运行的生产流水线，从需求输入生成配置交付包并保存真实执行日志。
