# MVP 技术选型与替代方案

| 领域 | MVP 决策 | 暂不选择 | 重评估触发条件 |
|---|---|---|---|
| 应用结构 | 模块化 Python 项目，保持层次边界 | 一开始拆成许多微服务 | 独立扩缩容/隔离需求经过验证 |
| 本体表达 | JSON 词汇 + JSON Schema + Python 语义校验 | 一开始部署完整 RDF/OWL 图平台 | 需要互操作、复杂图查询或正式推理 |
| 工作流 | 显式状态机 + 持久化运行记录作为参考实现 | 自由 Agent 对话或两套顶层状态机 | 长任务/分布式高可用需求推动评估成熟引擎 |
| 本地存储 | SQLite 用于测试和单机演示 | 宣称其为多节点生产数据库 | 多实例并发/高可用需求出现 |
| 工具集成 | Adapter 对接 Git/CI/API/MCP/扫描器 | 重写成熟工程平台 | 现有工具不满足验证过的需求 |
| 执行 | 固定任务、参数化调用、白名单与超时 | 模型直接执行任意 Shell 字符串 | 任何沙箱升级都需威胁建模和独立评审 |
| 模型依赖 | LLM 可替换，基础契约校验不依赖模型 | 模型作为唯一事实或授权来源 | 不改变此安全边界 |
| 产品切入 | Kafka 风格配置验证与交付 | 重写/编译 Kafka 上游 | 接入可信上游制品和真实集群后再扩展 |

选型不是行业通用答案。新增选择或改变关键边界需通过 ADR，记录背景、备选、代价、风险和重评估触发条件。
