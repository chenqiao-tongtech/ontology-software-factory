# 软件工厂 MVP：范围与非目标

## 1. 目标

在受控的参考环境中搭建一条小而完整的软件生产闭环：从结构化需求和已批准的软件资产开始，产生配置或代码变更，调用真实构建与测试工具，依据可验证的质量结果决定能否进入交付阶段，并留下可追踪记录。

首个贯穿案例是围绕**现有、经过审核的 Kafka 版本**生成和验证标准配置与客户化配置。这个案例用于验证工厂流程，不代表本项目负责开发 Kafka 本身。

## 2. MVP 包含

- 结构化需求输入及来源追踪。
- 资产目录中已批准组件和明确版本的选择。
- 客户化配置的机器可执行校验。
- 隔离环境中的真实构建与测试执行。
- 基于测试和安全工具实际结果的质量门禁。
- 关联源代码提交、构建、测试、候选制品与交付记录。
- 发布前人工审批；高风险生产动作不由 Agent 自主执行。

## 3. MVP 不包含

- 从零重写 Kafka 或其他成熟中间件。
- 不受限地自动开发任意规模的定制软件。
- Agent 直接持有生产环境管理员凭证。
- 无人工确认的生产发布、删除、迁移或密钥操作。
- 替代现有 Git、CI、测试、安全扫描、制品管理或部署平台。
- 一开始就建设复杂的全局知识图谱或通用推理引擎。
- 宣称“零人工”“零缺陷”或未经实测的效率提升比例。

## 4. 范围变更规则

新增能力必须同时写明：要解决的具体问题、复用现有产品还是自建、需要的权限与数据、验收证据、成本和风险。若能力改变了非目标或发布边界，应新增 ADR 并更新 `config/mvp-scope.json`、架构文档和验收清单。

## 5. 验收的基本原则

- “Agent 说完成了”不是证据。
- 构建必须有执行器记录、退出码和日志。
- 测试必须有真实执行结果，不能由模型自行编写通过报告。
- 安全门禁必须绑定具体提交或制品版本。
- 发布必须可追溯到审批、环境、版本和回退方案。
