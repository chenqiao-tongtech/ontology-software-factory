# ADR 0014：在大规模编码前冻结软件工厂总体设计基线

- 状态：Accepted
- 日期：2026-10-29
- 决策范围：第 15 篇规划基线；后续变更通过新的 ADR 修订

## 背景

单独维护 MVP 目标不足以指导后续多子系统协作。项目需要共同的架构视图、模块职责、接口、依赖、本体路线、不可绕过的约束和阶段退出条件。否则每篇文章可能各自加模块，造成职责和验收标准漂移。

## 决策

采用分层总体架构和机器可读 `config/architecture-baseline.json`。模块按职责拆分，并标记 `implemented` / `partial` / `planned`。本体 MVP 采用 JSON 词汇表、JSON Schema 和 Python 跨对象校验；只有在有明确需求时再引入 RDF/OWL/SHACL。工作流和执行面分离，工具授权由 IAM/策略组件决定，生成与验证分离，质量证据不足时 fail closed。

## 备选方案

1. 仅用一张架构图：简单，但模块责任、状态、依赖和验收不便机器检查。
2. 一开始建立完整企业本体和图数据库：成本过高，尚无明确需求证明其必要性。
3. 让 Agent 框架定义全部业务对象与流程：会导致语义和业务边界绑定某个框架。

## 后果

- 第 16–24 篇可以按统一基线逐项实现；
- 架构变化需同步更新基线、文档、验收及测试；
- `PASS` 只适用于有真实可复现证据的具体验收项；
- 本项目不会声称有真实 Kafka 集群部署或生产 IAM，除非实际接入并验收。
