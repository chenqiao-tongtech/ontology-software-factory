# ADR 0007：显式工作流状态机与运行控制台

- **状态：** Accepted（MVP 参考实现）
- **日期：** 2026-10-27
- **上下文：** Article 18 已定义 Agent 角色、Skill、工具权限与任务交接契约；还需要确定性规则将这些契约编排成一条可审计的运行路径。

## 决策

1. 区分 Workflow Definition、Workflow Run、Workflow Step、Attempt、Evidence 与 Event。
2. 用有向无环图表达节点依赖，MVP 中拒绝环路。
3. Run 与 Step 使用分开的状态集合；状态转换必须由后端状态机验证。
4. 人工审批是独立的 Human Step / Gate，不由 Agent 自我批准。
5. 每次状态变更必须在同一 SQLite 事务内写入 Run 状态和 Event，并使用 `revision` 做乐观并发检查。
6. 提供轻量 Web 控制台展示事实并提交状态机命令；控制台不直接调用 Shell、CI/CD 或部署工具。
7. 使用 Python 标准库实现本地 demo，避免将演示绑定到某个 LLM、云厂商或前端框架。

## 后果

**积极影响：** 状态与审计可测试；用户可以查看失败节点、尝试次数、证据占位与审批理由；不合法操作会被拒绝；可在后续替换 Store 与执行器而保持业务状态机边界。

**代价与限制：** 当前 SQLite 适合本地演示，不是多副本分布式执行数据库；没有 Worker、身份认证、后台超时扫描或事务型发件箱；当前页面将 DAG 展示为有序列表，不是通用流程设计器。

## 备选方案

- **单纯事件日志 + Prompt：** 难以保证依赖、审批门与状态转移的一致性，拒绝。
- **浏览器直接调工具：** 破坏后端授权边界，失败后也难以确保审计，拒绝。
- **立即引入第三方分布式工作流引擎：** 可能是生产的正确选择，但本阶段先明确领域模型和接口，之后再对接 Temporal、Step Functions 或已有平台。
