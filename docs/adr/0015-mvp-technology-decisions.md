# ADR 0015：选择轻量、可替换的 MVP 技术栈

- 状态：Accepted
- 日期：2026-10-29
- 关联：ADR 0001（MVP 边界）、ADR 0002（集成优先）、ADR 0004（JSON Schema 优先）和 ADR 0014（总体设计基线）

## 背景

软件工厂的第一阶段需要优先验证真实业务链路、语义契约和证据追踪，不应因为未来可能采用分布式工作流或形式化图推理，就提前引入尚无明确需求证明的基础设施。

## 决策

1. 采用模块化 Python 项目和清晰的包边界，暂不拆分大量微服务。
2. 核心本体采用 JSON 词汇表、JSON Schema Draft 2020-12 与 Python 语义校验；只有在互操作或推理需求明确时再评估 RDF/OWL/SHACL。
3. 将模型和 Agent 框架视为可替换 Adapter；基础契约校验和安全门禁不依赖模型推理结果。
4. 工作流采用显式状态机；本地参考实现可用 SQLite，不能将其描述为多节点生产级队列。
5. 优先适配现有 Git、CI、测试、扫描和制品平台，而不是在工厂内部重写它们。
6. 执行器只运行明确注册的任务和参数化命令，设置超时、工作区边界和日志采集；真实容器/微虚机隔离单独评审。
7. Kafka 首版只用于配置验证与候选配置交付，不下载、构建或重新发布 Kafka 上游二进制。

## 未选择的替代方案

- 一开始部署完整企业知识图谱/三元组库：暂缓，因当前的核心能力问题可由结构化契约和关系校验覆盖。
- 一开始拆成分布式微服务：暂缓，因会增加部署、认证、网络故障和本地开发复杂度。
- 自建 Git/CI/安全扫描/制品管理：不采用，优先组合成熟系统。
- 让模型拥有任意 Shell 和生产凭证：拒绝，违反默认拒绝与最小权限原则。

## 重新评估触发条件

出现多节点高可用、复杂长任务编排、强制图语义互操作、受控生产级沙箱、真实 Kafka 二进制交付或明确的企业 IAM 集成需求时，需提交新的 ADR，分析数据/安全/运维代价并附可复现 POC。
